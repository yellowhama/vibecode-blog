# 바이브코딩 풀스택! 진짜 AI 풀스택 개발이란 무엇인가, 광고식 가짜와 실전 차이

TL;DR (SEO 최적화 요약)

- 가짜 풀스택: Claude Code + n8n = 단순 이메일 자동화
- 진짜 AI 풀스택 개발: 아이디어 → SpecKit 문서화 → Rust+Godot 구현 → 자동 테스트 → pre-commit 검증 → CI/CD 배포
- 핵심 키워드: AI 풀스택 개발, 바이브코딩, SpecKit, Rust Godot 게임개발, 자동화 파이프라인, 테스트 자동화, CI/CD 배포, 프로그래밍없이개발

## 인스타 광고에 속을 뻔했다 – "바이브코딩 풀스택"이란 말의 진짜 의미

"바이브코딩 풀스택! Claude Code + n8n으로 개발자 되기!"

n8n? 그거 그냥 "이메일 오면 슬랙에 알림" 만드는 자동화 도구잖아. 그걸로 풀스택이라니. 우리 아들 걷기 시작했다고 우사인 볼트랑 경주하자는 거랑 뭐가 달라?

진짜 바이브코딩 풀스택이 뭔지 보여주겠다. 내가 지금 만들고 있는 축구 선수 육성 게임으로 말이다.

---

## 바이브코딩 풀스택 정의 – 아이디어에서 배포까지 전체 자동화 파이프라인

한 줄 정리: 하고 싶은 걸 말로 풀면 → 버튼 몇 번(스크립트) → 엔진이 굴러가고 → 검사관(테스트)이 통과하면 → 공장(CI/CD)이 포장·배송(빌드/배포)까지 자동으로 해주는 방식.

이게 "대화로 즉흥 제작(바이브 코딩)" + "전체 공정(풀 스택)"의 진짜 의미다.

n8n으로 이메일 자동화? 그건 풀스택의 한 조각일 뿐이다. 진짜는 아이디어가 실제 제품이 되는 전체 파이프라인을 자동화하는 거다.

---

광고식 풀스택 vs 진짜 AI 풀스택 개발 – 비교표로 보는 핵심 차이

| 구분 | 광고식 풀스택 (Claude+n8n) | 진짜 풀스택 (아이디어→배포) |
| --- | --- | --- |
| 범위 | 일부 자동화 (이메일·알림) | 스펙 → 구현 → 테스트 → 검증 → 배포 전체 자동화 |
| 시작점 | 코드 조각 + 워크플로우 | SpecKit 문서·폴더·계획 자동 생성 |
| 구현 | 도구 연결 위주 | Rust(엔진) + Godot(화면) + GDExtension 통합 |
| 품질 | 수동 확인 | proptest · insta · gdUnit4 자동 테스트 |
| 검증 | 없음 | pre-commit로 망가진 커밋 차단 |
| 배포 | 수동 | CI/CD로 멀티플랫폼 자동 빌드·배포 |

---

## 내가 실제로 만드는 게임 – 고등학교 3년 축구 선수 육성 시뮬레이션

고등학교 3년 동안 축구 선수를 키워서 프로로 만드는 게임이다. 우마무스메처럼 훈련시키고, FM처럼 경기하고, 파워프로처럼 이벤트가 터진다.

이 게임을 어떻게 만드는지, 아이디어부터 배포까지 전체 과정을 보여주겠다. 이게 진짜 풀스택이다.

앞으로 나올 7개 마법이 바로 이 시스템의 핵심이다. 각각이 뭘 하는지, 어떤 도구를 쓰는지, 왜 필요한지 전부 보여주겠다.

---

### SpecKit으로 자동 기획 문서 작성 – 아이디어를 구조화하는 첫 번째 마법

도구: GitHub SpecKit | 역할: 아이디어→문서→폴더 자동 생성

"고등학교 축구 선수 육성 게임 만들고 싶어. 3년 동안 훈련시켜서 프로 만드는 거야."

SpecKit은 내가 설명한 요구를 정리해 문서로 변환하고, 폴더 구조까지 자동으로 세팅한다.

---

### Bash 스크립트로 반복 작업 제거 – 자동화 버튼의 두 번째 마법

도구: Bash Scripts | 역할: 귀찮은 준비작업 3초 완료

폴더 생성, 브랜치 생성, 템플릿 복사를 버튼 하나로 끝낸다.

---

### Rust와 Godot으로 실제 게임 제작 – 빠른 계산과 가벼운 화면 엔진의 세 번째 마법

Rust는 계산 엔진이다. 내 실제 파이프라인에서 Python 기준 45분이 걸리던 게 Rust로 약 1.5분으로 줄었다(약 30배, 케이스 의존).

Godot은 화면을 담당한다. Unity 에디터(+모듈)는 수 GB급이지만, Godot은 에디터/빈 빌드 기준 수십~수백 MB 수준이라 체감 경량성 차이가 크다.

---

### 오픈소스 적극 활용 – GitHub에서 레고 조립하듯 가져오는 네 번째 마법

GitHub에는 축구 시뮬레이션 엔진(예: ZOXEXIVO/open-football, Apache-2.0)과 공개 데이터셋(예: openfootball/*, CC0)이 있다. 이를 라이선스 조건에 맞춰 선별 통합해 활용했다.

---

### 자동 테스트 로봇 3총사 – 밤새 품질을 보장하는 다섯 번째 마법

도구: proptest + insta + gdUnit4 | 역할: 24시간 자동 품질 검사

막 흔들기, 사진 대조, 실제 게임 플레이까지 로봇이 대신 돌려준다.

---

### Pre-commit 훅 문지기 – 망가진 커밋을 차단하는 여섯 번째 마법

pre-commit 훅은 테스트나 문서 업데이트가 통과되지 않으면 커밋 자체를 막는다. 팀 협업에서 특히 중요하다.

---

### CI/CD 자동 빌드 공장 – 멀티플랫폼으로 배포하는 일곱 번째 마법

GitHub Actions로 Windows, Mac, Linux, Android까지 자동 빌드가 가능하다. 단, Export Templates·키스토어·시크릿 설정이 필요하다.

---

현재 내 게임의 진행 현황 – 실전 데이터로 본 개발 퍼센트

- 완료: 육성 85%, 훈련 70%, 이벤트 50개
- 진행: 경기 40%(전술 세트 확보), 리플레이 30%
- 대기: 감독/코치 5%, 멀티 0%

---

광고식 가짜 vs 진짜 AI 풀스택 – 정리 요약표로 한눈에 보는 차이

| 항목 | 광고식 풀스택 | 진짜 풀스택 |
| --- | --- | --- |
| 문서화 | 없음 | SpecKit 자동 문서화 |
| 자동화 | n8n 일부 워크플로우 | 전체 파이프라인 자동화 |
| 테스트 | 수동 점검 | 로봇 3총사 자동 테스트 |
| 배포 | 수동 | CI/CD 자동 멀티플랫폼 빌드 |
| 검증 | 없음 | pre-commit 품질 게이트 |

---

코딩 몰라도 된다 – 감독은 나, 작업은 시스템이 한다

나는 "훈련 주 5회", "경기는 토요일" 같은 지시만 내린다.

시스템이 코드를 만들고, 테스트를 돌리고, 빌드하고, 배포한다.
