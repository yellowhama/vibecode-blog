# 한글 콘텐츠 바이브 코딩 시대가 왔다

# "AI야, 이거 전부 다 네가 짜줘" - 바이브 코딩 시대가 왔다

## AI가 코드 짜는 시대, 개발자는 뭘 해야 하나?

요즘 개발자들 사이에서 "바이브 코딩(Vibe Coding)"이라는 말이 돌고 있다. 영어로 "vibe"는 "느낌, 분위기"라는 뜻인데, "대충 느낌으로 코딩한다"는 건가? **바이브 코딩’은 2025년 2월, OpenAI 공동 창립자이자 전 테슬라 AI 책임자였던 Andrej Karpathy 대중화한 용어.** 개발자가 자연어로 목표를 설명하면 LLM이 코드를 생성하고, 사람은 품질을 검토·수정한다는 접근이다. Karpathy는 바이브 코딩에 대해 이렇게 말했다.

“코드는 사실상 존재하지 않는 듯한 느낌으로, 자연어로 말을 하고, 실행하고, 복사 붙여 넣기만 하면 대부분 작동한다.”

예전엔 개발자가 코드를 한 줄 한 줄 정확히 짰다. "이 변수는 정확히 이렇게, 이 함수는 정확히 저렇게..." 그런데 바이브 코딩은 다르다. 개발자가 "음... 대충 쇼핑몰 같은 거 만들어줘"라고 하면 AI가 전체 코드를 짠다. 개발자는 "느낌이 좀 다른데? 여기 좀 바꿔줘" 정도만 한다. 마치 "느낌적인 느낌으로" 코딩하는 것 같다고 해서 이런 이름이 붙었다.

이게 농담처럼 들리겠지만, Y Combinator의 매니징 파트너 Jared Friedman이 최근에 충격적인 발표를 했다. 2025년 W25 배치에 참여한 스타트업 중 약 25%가 코드의 95% 이상을 AI로 생성했다는 거다. Y Combinator는 에어비앤비, 드롭박스 같은 유명 기업들을 키워낸 곳이다. 거기서 투자받는 회사 4개 중 1개가 사실상 AI에게 코딩을 맡긴다는 얘기다.

핵심은 간단하다. AI가 코드를 주도적으로 짜고, 개발자는 가끔 손보는 정도만 한다. 예전엔 개발자가 코드 짜다가 막히면 AI한테 도움을 요청했다. 지금은 반대다. AI가 쭉쭉 코드를 짜고, 개발자는 문제가 생겼을 때만 개입한다.

이런 현실을 반영하듯, 최근 Software 저널에 흥미로운 논문이 실렸다. "Designing Microservices Using AI"라는 제목의 체계적 문헌 검토(Systematic Literature Review)였다. 아르헨티나와 부에노스아이레스 대학 연구팀이 2018년부터 2024년까지 나온 연구 43개를 싹 다 분석한 거다.
이 논문이 뭘 다뤘냐고? AI가 **마이크로서비스** 설계를 어떻게 자동화하고 개선하는지를 종합적으로 정리했다. 쉽게 말해서 "AI한테 시스템 설계까지 맡길 수 있나?"에 대한 학계의 대답이다.

## 마이크로서비스 설계가 왜 어려운가

큰 프로그램 하나를 작은 서비스 여러 개로 나누는 게 마이크로서비스다. 중국집으로 비유하면 이해가 쉽다.

진짜 중국집은 간단하다. "배달~ 짜장 두 개, 탕수육 하나 세트~" "네에~" 끝이다.

컴퓨터가 운영하는 중국집은 어떨까? 같은 주문이 들어오면 이런 일이 벌어진다.

주문 서비스가 재고 서비스한테 묻는다. "면 2인분 있나요?" 재고 서비스가 답한다. "확인 중... 네." 주문 서비스가 또 묻는다. "춘장은요?" "확인 중... 네." "돼지고기는?" "확인 중... 네."

그다음엔 주문 서비스가 면 삶기 서비스한테 "2인분 삶아주세요", 짜장 볶기 서비스한테 "2인분 볶아주세요", 탕수육 서비스한테 "1인분 튀겨주세요" 지시한다. 면 삶기 서비스는 짜장 볶기 서비스한테 "면 준비됐어요" 알리고, 탕수육 서비스는 소스 담기 서비스한테 "소스 담았어요" 알린다.

사람은 2마디면 끝날 일을 컴퓨터는 30번 통신한다.

더 큰 문제가 뭔지 아는가? 소스 서비스가 고장나거나 소스가 떨어지면 탕수육을 못 만든다. 전체 주문이 멈춘다. 소스 새로 만드는 함수를 또 넣어줘야 한다. 사람은 어떻게 하나? 그냥 소스 만든다.

이래서 마이크로서비스 설계가 지옥이다. 어디까지가 하나의 서비스인지 정하기 애매하다. 너무 잘게 나누면 통신 지옥이 되고, 너무 크게 묶으면 나눈 의미가 없다. 경험 많은 개발자도 "단무지는 간단하니까 따로 빼자" 했다가, 나중에 모든 배달마다 단무지 서비스 호출하느라 시스템 느려지는 걸 경험한다.

## AI는 이 문제를 어떻게 풀까

최근 Software 저널에 흥미로운 논문이 실렸다. 2018년부터 2024년까지 나온 연구 43개를 분석한 체계적 문헌 검토였다. AI가 마이크로서비스 설계를 어떻게 자동화하고 개선하는지를 종합적으로 분석한 내용이다.

AI가 쓰는 방법은 크게 세 가지다.

첫 번째, 코드를 보고 패턴을 찾는다. 클러스터링이라는 기법을 쓴다. 쇼핑몰로 치면 이런 식이다. "상품 조회 함수"와 "재고 확인 함수"가 항상 같이 호출된다. 그럼 같은 서비스로 묶자. "결제 처리"와 "포인트 차감"도 항상 같이 일어난다. 이것도 같은 서비스로. AI는 이런 패턴을 수백만 개 찾아낸다. 사람이 일일이 분석하면 몇 달 걸릴 일을 몇 분 만에 한다.

두 번째, 요구사항 문서를 읽고 이해한다. "사용자는 상품을 검색할 수 있어야 한다", "사용자는 장바구니에 상품을 담을 수 있어야 한다", "사용자는 결제할 수 있어야 한다" 이런 문장들을 AI가 읽는다. 그리고 비슷한 기능끼리 묶는다. BERT라는 언어 모델을 쓰는 도구도 있다. BERT는 단어 하나하나가 아니라 문맥을 이해한다. "상품 검색"과 "제품 찾기"가 같은 뜻인 걸 안다.

세 번째, 실제 사용 패턴을 학습한다. 시스템이 돌아가면서 생기는 로그를 분석한다. 어떤 기능이 자주 쓰이는지, 어떤 서비스끼리 통신이 많은지 본다. 통신이 너무 많으면 서비스를 합친다. 한 서비스가 너무 크면 쪼갠다. 머신러닝으로 최적의 균형점을 찾는다.

## AI가 중국집을 설계한다면?

그래서 AI가 중국집 배달 시스템을 처음부터 설계한다면 어떻게 될까?

AI는 우선 과거 주문 데이터 100만 건을 분석한다. "짜장-탕수육 콤보는 90% 확률로 같이 주문되네?" 그럼 하나의 서비스로 묶자. "단무지는 모든 주문에 필요하네?" 따로 빼지 말고 주문 서비스에 포함시키자. "금요일 저녁 6-8시는 주문이 폭주하네?" 이 시간대에는 면 삶기 서비스를 3개로 늘려놓자.

컴퓨터는 멍청해서 "면 있나요?" "춘장 있나요?" 30번씩 통신한다. AI는 똑똑해서 "어차피 짜장면 주문이면 다 필요한 거잖아" 한 번에 처리한다. 마치 20년차 중국집 사장님이 "짜장 둘이요~" 소리만 듣고도 손이 알아서 움직이는 것처럼, AI도 패턴을 학습해서 쓸데없는 확인 절차는 다 생략한다.

결국 인간처럼 "대충" 하는데, 컴퓨터보다 훨씬 똑똑하게 "대충" 하는 셈이다.

## 실제 성과는 어떨까

논문이 분석한 43개 연구를 보면 실제로 효과가 있다.

IBM이 만든 Mono2Micro라는 도구가 있다. 이름 그대로 모놀리식, 그러니까 덩어리로 된 프로그램을 마이크로서비스로 쪼개주는 도구다. 이게 어떻게 작동하냐면, 먼저 코드를 죄다 스캔한다. 어떤 클래스가 어떤 클래스를 부르는지, 어떤 데이터를 같이 쓰는지 다 분석한다. 그다음엔 이걸 그래프로 만든다. 마치 지하철 노선도처럼 연결 관계를 그린다.

그래프가 완성되면 AI가 칼질을 시작한다. 연결이 많은 놈들끼리는 한 덩어리로, 연결이 적은 놈들은 따로 떼어낸다. 실제 기업에서 써봤더니 사람이 몇 주 걸려서 하던 일을 며칠 만에 끝냈다고 한다. 더 중요한 건, 사람이 놓치기 쉬운 숨은 의존성까지 찾아낸다는 거다. "어? 이 코드가 저기랑 연결되어 있었어?" 하는 것들 말이다.

SEMGROMI는 좀 다른 접근을 쓴다. 이건 코드를 보는 게 아니라 사용자 스토리를 본다. 사용자 스토리가 뭐냐면, "사용자는 로그인할 수 있어야 한다", "사용자는 상품을 구매할 수 있어야 한다" 이런 요구사항들이다.

SEMGROMI는 이 문장들을 읽고 비슷한 것끼리 묶는다. 예를 들어 "로그인", "비밀번호 재설정", "회원가입"은 다 사용자 인증과 관련된 거니까 하나의 서비스로 묶는다. "상품 조회", "상품 검색", "카테고리 탐색"은 상품 서비스로 묶는다. 단순해 보이지만, 문장이 수백 개가 되면 사람이 하기엔 머리가 터진다. SEMGROMI는 이걸 자동으로 해준다.

재미있는 건, 이 도구가 결합도와 응집도라는 걸 개선한다는 거다. 결합도는 서비스끼리 얼마나 끈끈하게 붙어있는지를 말한다. 낮을수록 좋다. 서로 독립적이어야 하나를 고쳐도 다른 게 안 망가진다. 응집도는 한 서비스 안의 기능들이 얼마나 관련 있는지를 말한다. 높을수록 좋다. 관련 있는 것끼리 모여있어야 관리가 쉽다.

SEMGROMI가 그룹핑한 결과를 보면, 사람이 대충 나눈 것보다 결합도는 낮고 응집도는 높다. 컴퓨터가 사람보다 더 체계적으로 분류한다는 얘기다.

물론 이런 도구들이 만능은 아니다. 초안을 만들어주는 정도다. 최종 결정은 여전히 사람이 해야 한다. 하지만 맨땅에서 시작하는 것보다는 훨씬 낫다. 마치 빈 캔버스보다 밑그림이 있는 캔버스가 그리기 쉬운 것처럼.

## 아직 못 푸는 문제들

그렇다고 AI가 만능은 아니다. 아직 못 푸는 문제들이 있다.

데이터 일관성 문제가 대표적이다. 주문 서비스는 "주문 완료"라고 저장했는데 재고 서비스는 "재고 부족"이라고 한다. 이런 불일치를 어떻게 막을까? AI도 아직 답이 없다.

분산 트랜잭션도 골치다. 결제는 성공했는데 배송 등록이 실패했다. 결제를 취소해야 하나? 재시도해야 하나? 복잡한 시나리오를 AI가 다 예측하기 어렵다.

애매한 요구사항도 문제다. "사용자 친화적으로 만들어주세요", "성능이 좋아야 해요" 이런 모호한 요구사항은 AI도 해석 못한다. 구체적인 숫자가 필요하다.

실시간 피드백도 아직이다. AI가 설계한 대로 만들었는데 실제로는 문제가 생긴다. 운영하면서 나온 데이터를 다시 설계에 반영하는 건 아직 연구 중이다.

## 미래는 어떻게 될까

논문은 몇 가지 트렌드를 짚는다.

생성형 AI의 등장이 가장 큰 변화다. ChatGPT 같은 대규모 언어 모델이 설계를 도와준다. "온라인 쇼핑몰을 마이크로서비스로 설계해줘"라고 하면 전체 구조를 제안한다.

강화학습도 적용되고 있다. 시스템이 스스로 학습한다. 트래픽이 늘면 자동으로 서비스를 확장한다. 오류가 자주 나는 부분은 자동으로 개선한다.

가장 현실적인 건 하이브리드 접근이다. AI가 초안을 만들고 사람이 검토한다. AI가 놓친 부분을 사람이 잡는다.

## 그래서 어떻게 써야 하나

이제 스페인어를 아예 못해도, 스페인에 놀러가서 많은 걸 즐길수 있다. 

번역 어플을 꺼내면 되니까. 

물론 스페인어를 잘하는 사람보다는 조금 불편하다.  

코딩을 한줄도 못적어도, 이제 코드를 짜고 프로그램을 만들고 어플을 만들수 있다. 

물론 진짜 개발자들 보다는 많이 불편하다.

중요한건 가능하다는거다. 불가능이 가능이 되었다. 

불편함쯤은 감수할수 있다. 이제 너도 나도 개발자가 될수가 있는거다. 

이게 바이브 코딩 시대의 개발자다. 

자 무엇을 해야할까?
컴퓨터에 우분투를 깔자. 

그리고 클러드 코드를 깔아보자. 

자 모든게 준비 되었다. 

개발을 해볼까?
