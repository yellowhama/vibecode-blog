# **Spec Kit 실전기: AI 코딩 계획이 현실에서 깨지는 순간**

## TL;DR (3줄 요약)

- **계획은 계획일 뿐** — 빌드 타임아웃, 기존 코드 충돌, 성능 저하 같은 현실의 펀치가 먼저 날아온다.
- **AI 3인 협업 패턴** — Claude Code(실행), GPT(분석), Cursor(정리)로 문제를 풀고 기록하며 진화한다.
- **핵심 교훈** — 완벽한 계획은 없지만, 기록·문서화·패턴화로 더 안정적이고 빠른 AI 코딩이 가능하다.

## 완벽한 계획, Spec Kit

011편에서 Spec Kit으로 계획 다 짰다. 20개 FR(Functional Requirements), 4단계 프로세스, Phase별 구현 계획. 뭐 깔끔했다.

전술 시스템 구현하기로 했고, T1.1부터 순서대로 하면 되는 거였다. Rust로 백엔드 만들고, Godot으로 연동하고, UI 붙이고.

"이제 /implement만 치면 되겠네."

마이크 타이슨이 그랬다더라. "계획은 누구에게나 있다, 쳐맞기 전까지는."

## 첫 번째 펀치: 빌드가 안 된다

Spec Kit에서 `/implement T1.1` 엔터.

이게 뭐냐면, Spec Kit이 작업을 쪼개놓은 게 있다. T1.1, T1.2, T1.3... 이런 식으로. 각각이 할 일 하나씩이다. T1.1은 "Rust로 전술 엔진 만들기"였다.

Claude Code가 열심히 파일들을 만들기 시작했다. Rust 코드가 쭉쭉 생성됐다. 500줄, 1000줄... 전술 계산하는 코드, 포메이션 관리하는 코드.

다 만들고 나서 컴파일을 시작했다. 이건 코드를 실제로 사용할 수 있는 파일로 만드는 과정이다. 밀가루 반죽을 오븐에 넣어서 빵으로 만드는 것처럼.

1분... 괜찮아, Rust 빌드는 원래 좀 걸려.

2분... 어? 왜 이렇게 오래 걸리지?

`Build timeout: Process exceeded 2 minutes`

타임아웃. 오븐에 불이 안 들어오는 거였다.

> 💡 실제 문제 분석
> 
> 
> ```
> cargo build --release
> Compiling godot-codegen v0.1.0 (git+...)
> Building [=>        ] 13/88 crates
> 
> ```
> 
> godot dependency가 git master branch를 쓰고 있어서 매번 재컴파일.
> 88개 crate 중 13개만 캐시되고 나머지는 처음부터 다시 빌드.
> 

## AI 삼종세트 출동

이럴 때 쓰는 패턴이 있다.

먼저 Claude Code한테 진단을 시켰다.

"현재 상황 파악해서 문제점 정리해."

Claude Code가 빌드 로그를 뒤져서 정리해줬다. 뭔가 계속 똑같은 걸 반복 컴파일하고 있었다.

이 정보를 GPT한테 들고 갔다.

"이 문제 어떻게 해결해?"

GPT가 해결책을 제시했다. 버전을 고정하고, 빌드 캐시를 쓰라고.

> 💡 해결책 구현
> 
> 
> ```toml
> # Cargo.toml 수정
> - godot = { git = "...", branch = "master" }
> + godot = "0.3.5"
> 
> ```
> 
> - sccache 설치로 빌드 캐시 활성화
> - rust-lld 링커 사용으로 링킹 속도 개선
> - 결과: 2분 타임아웃 → 28초 성공

다시 Claude Code한테 돌아와서 실행시켰다. 28초. 성공했다.

## 두 번째 펀치: 아, 이미 있었네?

T1.2로 넘어갔다. 전술 시스템 관리하는 파일을 만들려고 했다.

Claude Code가 갑자기 멈춰서 말했다.

"어... 여기 이미 전술 관련 코드가 있는데요?"

확인해보니 정말 있었다. CoachSystem이라는 파일에 전술 관련 코드가 이미 들어있었다.

이게 뭔 상황이냐면, 새 집 짓는다고 땅 파고 있는데 거기 이미 지하실이 있던 거다. "어? 여기 이미 기초공사 되어있네?"

Spec Kit은 이걸 몰랐다. 당연하지. 내가 "아 참고로 여기 이미 전술 코드 조금 있어"라고 안 말했으니까.

> 💡 기존 코드 발견
> 
> 
> ```
> # scripts/core/CoachSystem.gd
> current_tactics = "4-4-2"
> available_tactics = ["4-4-2", "4-3-3", "3-5-2"]
> func change_tactics(new_tactics: String) -> void:
>     # 이미 구현되어 있음
> 
> ```
> 
> 문제: Spec Kit은 이 파일의 존재를 몰랐음
> 해결: 기존 시스템 확장 방식으로 통합
> 

## AI 팀플레이로 해결

혼자서는 못 풀 문제였다. 그래서 AI 3명을 다 동원했다.

먼저 Claude Code한테 정찰을 시켰다.

"기존 파일에 뭐가 있는지 다 조사해."

Claude Code가 파일을 열어서 읽어봤다. "포메이션 4-4-2, 4-3-3, 3-5-2가 이미 있고요. 전술 바꾸는 기능도 있네요."

이 정보를 가지고 GPT한테 갔다.

"이미 있는 코드랑 새로 만들 코드를 어떻게 연결하지?"

GPT가 작전을 짜줬다. "기존 걸 버리지 말고 확장하세요. 기존 코드는 '코치 시스템', 새 코드는 '전술 실행 시스템'으로 역할을 나누면 됩니다."

> 💡 통합 아키텍처
> 
> 
> ```
> CoachSystem (기존)     TacticalManager (신규)
>     ↓                        ↓
> 전술 지식 관리         실제 전술 실행
> 감독-코치 관계         Rust 백엔드 연동
> 전술 학습              실시간 효과성 계산
>     ↓_____Signal_____↓
>           연동 완료
> 
> ```
> 

Claude Code가 두 시스템을 연결했다. 기존 시스템이랑 새 시스템이 서로 대화하도록.

## 세 번째 펀치: 버벅거린다

포메이션 화면을 만들었다. 축구장 그림 위에 선수 11명 배치하는 거.

근데 실행해보니 뭔가 버벅거렸다. 목표는 초당 60번 화면이 바뀌어야 하는데(60fps), 45번밖에 안 바뀌는 거다(45fps).

게임할 때 프레임 떨어지면 답답한 거 알지? 그거랑 똑같은 상황.

Spec Kit 계획서 보니까 "성능 최적화는 나중에(Phase 5)"라고 되어있더라. 지금은 Phase 1인데...

> 💡 성능 병목 분석
> 
> 
> ```
> # FormationDisplay.gd 문제 코드
> func _draw():
>     draw_field()      # 매 프레임 전체 필드 다시 그림
>     draw_all_players() # 11명 전부 다시 그림
>     draw_all_lines()   # 모든 라인 다시 그림
> 
> ```
> 
> 원인: 변경 없어도 초당 60번 전체 재렌더링
> 해결: Dirty flag 패턴 + 캐싱
> 

## 문제 해결 콤보

**1단계: 진단**

Claude Code한테 "왜 느려?"라고 물었다.

"매번 전체 화면을 다시 그리고 있어요. 초당 60번씩 전체를요."

**2단계: 처방**

GPT한테 이 상황을 설명했다.

"변경된 부분만 다시 그리게 하세요. 전체를 매번 그릴 필요 없어요."

**3단계: 실행**

Claude Code가 코드를 고쳤다. 바뀐 부분만 다시 그리도록.

**4단계: 마무리**

Cursor로 전체 코드를 깔끔하게 정리했다.

> 💡 최적화 결과
> 
> 
> ```
> # 개선된 코드
> var needs_redraw = false
> 
> func _draw():
>     if not needs_redraw:
>         return
>     # 변경된 부분만 그리기
>     needs_redraw = false
> 
> ```
> 
> 결과: 45fps → 60fps 달성
> 

## 중요한 깨달음: 문제를 기록하자

다음날, 똑같은 빌드 문제가 또 생겼다.

"어? 어제 해결했는데... 어떻게 했더라?"

기억이 안 났다. Claude Code도 새 대화라서 모른다.

그때부터 모든 문제와 해결법을 기록하기 시작했다.

"Claude Code야, PROBLEMS.md라는 파일 만들어. 문제 생길 때마다 여기 적어."

> 💡 PROBLEMS.md 예시
> 
> 
> ```markdown
> ## 빌드 타임아웃 문제
> - 증상: 2분 넘게 빌드가 안 끝남
> - 원인: godot이 매번 재컴파일됨
> - 해결:
>   1. godot 버전을 0.3.5로 고정
>   2. sccache 설치 (또는 build_without_sccache.sh 사용)
>   3. rust-lld 링커 활성화
> - 결과: 2분+ → 28초
> 
> ```
> 

이렇게 적어놨더니 일주일 후 같은 문제 생겼을 때 5초 만에 해결했다.

## AI 협업 패턴 정립

이렇게 몇 번 하다보니 패턴이 보였다.

```
문제 발생 → Claude Code(진단) → GPT(분석) → Claude Code(실행) → Cursor(정리)

```

각자 잘하는 게 달랐다:

- **Claude Code**: 손발 (파일 다루고 실행)
- **GPT**: 머리 (문제 분석하고 해결책 제시)
- **Cursor**: 청소부 (전체 코드 정리와 리팩토링)

> 💡 실제 작업 로그
> 
> 
> ```
> [09:23] Claude Code: "TacticsManager.gd 생성 시도"
> [09:24] Claude Code: "CoachSystem.gd에 충돌 발견"
> [09:25] GPT 상담: "통합 방안 제시"
> [09:27] Claude Code: "통합 구현 완료"
> [09:30] Cursor: "중복 코드 156줄 제거"
> 
> ```
> 

## 결과: 계획과 다르지만 더 나은

Spec Kit 계획대로라면 20개 FR을 순서대로 구현해야 했다.

실제로는:

- 8개 FR만 구현
- 대신 기존 시스템 통합
- 성능 최적화 미리 진행
- 빌드 시스템 정리
- 문서화 체계 구축

> 💡 구현 현황 (spec-tactics-system.md)
> 
> 
> ```markdown
> ## T1.2 IMPLEMENTATION COMPLETED
> ✅ FR-001: 매니저만 포메이션 선택 권한
> ✅ FR-002: 선수의 전술 지시 거부 불가
> ✅ FR-017: 포메이션 시각적 표현
> ✅ FR-018: 포메이션 선택 시 즉시 피드백
> 
> Phase 완료: 8/20 FR (40%)
> 하지만 안정성: 200% 향상
> 
> ```
> 

계획과 다르지만 더 안정적인 구조가 됐다.

## 바이브 코딩 실전 팁

문제가 생기면:

1. **당황하지 마** - 모든 개발자가 겪는 일
2. **AI한테 설명해** - "이거 안 돼"를 구체적으로
3. **여러 AI 활용** - 각자 잘하는 게 다름
4. **해결법 기록** - 나중에 또 쓸 거다
5. **계획 수정 OK** - 완벽한 계획은 없다

> 💡 문제 해결 프로세스
> 
> 
> ```
> 1. Claude Code: 상황 정리 (1분)
> 2. GPT: 해결책 분석 (2분)
> 3. Claude Code: 실행 (5분)
> 4. Cursor: 코드 품질 개선 (3분)
> 5. Claude Code: PROBLEMS.md 업데이트 (자동)
> 6. Spec Kit: 문서 업데이트 (/constitution 갱신)
> 
> ```
> 

## 에필로그: 계획대로 안 돼도 괜찮다

Spec Kit은 지도다. 하지만 실제로 길 걷다 보면 공사중일 수도 있고, 막혀있을 수도 있다.

그럴 때 AI들이 우회로를 찾아준다. 그리고 그 우회로를 문서로 남겨두면, 다음에는 더 빨리 갈 수 있다.

**계획은 누구에게나 있다, 쳐맞기 전까지는.**

쳐맞아도 괜찮다. 해결하고 기록하면 된다.

그것도 AI가 해주니까.
