# 복순이 대수술기: 스파게티 코드에서 시스템으로

## TL;DR

- **문제**: 로컬 LLM(GPU 16GB)으로 만든 5개 에이전트 ‘복순이’, 45분 실행·30% 실패율·1만줄 스파게티 코드.
- **해결**: GitHub Spec Kit으로 명세서 작성 → 공통 모듈화, 수집/평가 2단계 분리, GPU 언로드 자동화, 에러 3레벨 체계화.
- **성과**: 실행시간 **45분 → 12분**, 코드량 **10,847줄 → 3,562줄**, 실패율 **30% → 3%**, 새 소스 추가 **2일 → 2시간**.
- **Rust 도입**: 데이터 수집부만 Rust로 전환 → 속도 **30배↑**, 메모리 사용량 **80%↓**.
- **교훈**: AI는 요리사, 인간은 미슐랭 심사위원. 바이브 코딩은 출발점일 뿐, 명세서 기반 리팩토링으로 **시스템화**해야 진짜 효율이 나온다.

## 복순이가 멈춘 날

2024년 12월 어느 월요일 아침. 커피를 마시며 복순이 대시보드를 열었다. 텅 비어있었다.

"어? 복순이 또 삐졌나?"

로그를 확인해봤다. 복순이3이 arXiv에서 논문 다운로드하다가 타임아웃. 복순이1은 Product Hunt API 호출 중 에러. 복순이4는 아예 시작도 못했다. 5개 에이전트 중 정상 작동한 건 단 하나도 없었다.

디버깅을 시작했다. 그리고 충격적인 진실을 발견했다.

총 코드: 10,847줄. 중복 코드: 4,200줄. 복사-붙여넣기의 향연이었다.

전형적인 스파게티 코드였다. 

## 복순이가 뭐야?

복순이는 내가 만든 5개의 AI 에이전트 군단이다. 정보의 바다에서 허우적대는 나를 구하기 위해 태어났다.

매일 아침, 복순이들은 각자의 영역에서 일한다. 

**복순이1**은 인터넷을 뒤져서 새로운 AI 도구를 찾는다.

**복순이2**는 The Conversation 같은 학술 사이트에서 내가 원하는 주제의 과학 기사를 긁어온다.

**복순이3**은 arXiv에서 내가 원하는 주제의 AI 논문을 찾아온다.

**복순이4**는 대중심리학 논문중 ai과 관련된 걸 전문으로 다룬다. “AI와 실연: GPT 4o를 잃은 사람들은 어떻게 반응하고 있는가?" 같은 논문을 찾아온다.

**복순이5**는 직장인 전용이다. "ChatGPT로 회의록 작성 시간 90% 줄이기" 같은 실무형 연구만 골라온다.

이 녀석들은 로컬에서 돌아가는 오픈소스 AI 모델들을 쓴다. Solar 10.7B와 Qwen2.5 14B. OpenAI나 Anthropic API에 돈 낼 필요 없다. 내 컴퓨터에서 조용히 돌아간다. 가끔 GPU 메모리가 터질 것 같긴 하지만, 무료라는 게 어디야.

이 녀석들 덕분에 나는 더 이상 하루 종일 구글을 뒤지지 않아도 된다.
복순이가 매일 몇천개의 콘텐츠를 검토하고, 쓸 만한 50개만 골라준다.
내가 할 일은 그 url을 타고 들어가 그중에서 오늘 쓸 글감을 고르는 것뿐이다.
글감을 고르면 다시 복순들에게 따로 시킨다.

"이 주제에 대한 논문이나 사용 후기를 찾아줘."
한 주제에 글이 4-5개쯤 쌓이면 인사이트가 보이기 시작한다. 그럼 쓰기 시작!

문제는 이 5개가 각자 따로 놀았다는 거다. 

같은 RSS 파싱 코드를 5번 짰고, 같은 에러 처리를 5번 구현했다. 전형적인 바이브 코딩의 결과물이었다.

## 45분의 고통

복순이 전체를 한 번 돌리는데 평균 45분. 왜 이렇게 오래 걸릴까?

순차 실행이 원인이었다. 복순이1이 끝나야 복순이2가 시작한다. 병렬 처리? 불가능했다.

이유는 간단했다. 로컬 LLM을 쓰기 때문이다. Solar 10.7B와 Qwen2.5 14B를 동시에 돌리면? GPU가 즉사한다. 내 RTX 4060 ti의 16GB VRAM으로는 모델 하나도 아슬아슬한데, 두 개를 동시에? 꿈도 꾸지 마라.

그래서 복순이들은 차례를 기다려야 했다. 복순이1이 Solar 모델로 콘텐츠 평가를 끝내면, GPU 메모리를 비우고, 복순이2가 접속한다. 복순이3이 Qwen으로 논문을 요약하는 동안, 나머지는 대기실에서 기다린다. 

마치 하나뿐인 화장실을 5명이 돌려쓰는 것 같았다.

에러 처리도 엉망이었다. try-except로 대충 감싸놨지만, 어디서 에러가 났는지 알 수가 없다. "뭔가 잘못됐습니다"만 반복될 뿐. 가끔은 GPU 메모리 오류인지, API 타임아웃인지, 아니면 모델이 뻗은 건지도 구분이 안 됐다.

실패율 30%. 10번 중 3번은 제대로 작동하지 않는다. 타임아웃, API 제한, 웹사이트 구조 변경도 있지만, 가장 큰 문제는 "모델 언로드 실패"였다. 한 번 GPU에 올라간 모델이 제대로 내려오지 않으면, 다음 복순이는 아예 시작도 못했다.

## 명세서의 힘

지난 주에 GitHub Spec Kit에 대해 썼다. 이론은 충분했다. 이제 실전이었다.

Claude Code를 켰다. "복순이 코드 분석해서 명세서 만들어줘."

1시간 만에 15페이지 명세서가 나왔다. 충격적이었다. 내가 만든 시스템인데 처음 보는 내용들이 가득했다.

"복순이2와 복순이4가 동일한 arXiv API를 사용하는데 각각 다른 방식으로 구현되어 있습니다."

"에러 처리 코드가 전체의 60%를 차지하지만, 실제로는 3가지 패턴만 반복됩니다."

"5개 에이전트 중 3개가 동일한 마크다운 변환 로직을 사용하지만 각각 다르게 구현되어 있습니다."

## 대수술 시작

명세서를 바탕으로 리팩토링을 시작했다. Claude Code가 주도하고, 나는 방향만 제시했다.

첫 번째, 공통 모듈 추출. ContentSource라는 추상 클래스를 만들고, 모든 에이전트가 상속받도록 했다. RSS 파싱, 웹 스크래핑, 마크다운 변환 같은 공통 기능을 한 곳에 모았다.

두 번째, 영리한 비동기 처리. GPU는 여전히 병목이지만, 데이터 수집은 병렬로 할 수 있었다.

복순이들이 웹사이트를 스크래핑하고 API를 호출하는 동안은 GPU가 필요 없다. 그래서 작업을 두 단계로 분리했다. **수집 단계**에서는 5개 에이전트가 동시에 데이터를 긁어온다. RSS 피드, arXiv API, 웹 스크래핑을 asyncio로 병렬 처리. 이것만으로도 20분이 절약됐다.

**평가 단계**에서는 여전히 순차 처리다. 하지만 이제는 데이터가 이미 준비되어 있으니 모델 로딩 시간만 기다리면 된다. 게다가 배치 처리를 도입했다. 복순이1이 콘텐츠 30개를 한 번에 평가하도록. 모델을 한 번 올려서 최대한 많이 처리하고 내리는 방식이다.

세 번째, GPU 메모리 관리 자동화. `ollama stop` 명령을 각 에이전트 실행 후에 자동으로 넣었다. 모델이 GPU에 눌러붙는 문제가 사라졌다. 다음 복순이가 확실하게 깨끗한 메모리에서 시작할 수 있게 됐다.

네 번째, 에러 처리 표준화. 3가지 레벨로 분류했다. Critical(중단), Warning(계속하되 기록), Info(무시). GPU 메모리 오류는 Critical로 분류해서 즉시 모델을 언로드하고 재시작하도록 했다.

## Rust 전환: 예상 밖의 성공

"이왕 리팩토링하는 김에 Rust로 바꿔보자."

사실 나는 Rust가 뭔지도 잘 몰랐다. 그냥 성능 좋다는 글들을 읽었을 뿐이다.

Claude에게 물어봤다. "Python 코드를 Rust로 바꿀 수 있어?"

Claude의 답변은 비관적이었다. 

"Python 라이브러리 의존성이 너무 큽니다. BeautifulSoup, PyPDF2, yfinance... Rust로 완전히 재구현하려면 상당한 시간이 필요할 겁니다. 투자 대비 효과가 낮을 수 있습니다."

그런데 호기심에 Claude Code를 켜봤다. "복순이1 RSS 수집 부분만 Rust로 만들어봐."

왠걸? 20분도 안 돼서 작동하는 코드가 나왔다. feed-rs로 RSS 파싱, html2text로 마크다운 변환, reqwest로 HTTP 요청. tokio로 비동기 처리까지.

"어? 이거 되는데?"

**Python 버전**: 45분, 순차 처리, 메모리 500MB
**Rust 버전**: 1.5분, 동시 처리 20개, 메모리 100MB

30배 빨라졌다. Claude는 안 된다고 했는데, Claude Code는 해버렸다. 같은 회사 제품인데 이렇게 다를 수가. 이제 claude 놀리러 가야겠다. 

“안된다며?”

## 영리한 하이브리드 전략

비밀은 작업을 두 단계로 분리한 거였다.

**Phase 1: 데이터 수집 (병렬)**

- 19개 RSS 피드 동시 크롤링
- tokio 비동기 런타임으로 동시 처리
- GPU 필요 없음 → 무한 병렬 가능

**Phase 2: AI 평가 (순차)**

- Ollama로 콘텐츠 평가
- GPU 메모리 제약 → 하나씩 처리
- 하지만 데이터가 이미 준비되어 있어서 빠름

```
[데이터 수집: 20개 동시]
    ↓ (10초)
[모든 데이터 준비 완료]
    ↓
[LLM 평가: 1개씩 순차]
    ↓ (50초)
[완료: 총 1분]

```

이전에는 "수집→평가→수집→평가"를 반복했다. 이제는 "모두 수집→모두 평가"다.

Rust를 몰라도 상관없었다. Claude Code가 다 해줬으니까. 나는 그저 "이거 좀 고쳐줘", "에러 처리 추가해" 같은 요구만 했을 뿐이다.

Rust의 제로카피 연산과 타입 안정성 덕분에 메모리 사용량도 80% 줄었다. SQLite 중복 체크도 sqlx로 비동기 처리. 실패율도 30%에서 5%로 떨어졌다.

## 예상치 못한 발견들

리팩토링하다가 깨달은 것들이 있다.

**복순이3이 필요 없었다.** 복순이4(Dr. PopPsycho)가 이미 arXiv에서 논문을 가져오고 있었다. 단지 다른 카테고리일 뿐. 통합하니 코드가 30% 줄었다.

**점수 시스템이 무의미했다.** 90점 만점, 100점 만점... 사실 다 비슷했다. 결국 "좋다/보통/나쁘다" 3단계로 단순화했다.

**에러의 90%가 타임아웃이었다.** 복잡한 에러 처리보다 타임아웃 시간을 늘리고 재시도 로직을 넣는 게 효과적이었다.

## 새로운 복순이

리팩토링 결과가 놀라웠다.

**실행 시간**: 45분 → 12분. 병렬 처리의 마법이었다.

**코드량**: 10,847줄 → 3,562줄. 중복 제거와 모듈화 덕분이다.

**실패율**: 30% → 3%. 표준화된 에러 처리가 효과를 봤다.

**새 소스 추가**: 2일 → 2시간. ContentSource 인터페이스만 구현하면 끝이다.

가장 큰 변화는 유지보수다. 이제 어디가 문제인지 바로 알 수 있다. 로그가 체계적이고, 모듈이 독립적이라 디버깅이 쉽다.

## 80-20 법칙: AI가 요리사, 나는 미슐랭 심사위원

리팩토링하면서 깨달은 가장 중요한 사실이 있다.

AI가 이제 80%를 담당한다. 코딩, 테스트, 문서화, 심지어 버그 수정까지. 내가 하는 건 나머지 20%다. 명세서 쓰고, 품질 관리하고, 방향 제시하고.

예전엔 반대였다. 개발자가 80%를 코딩하고, 도구가 20%를 도와줬다. 

이제는 역할이 완전히 바뀌었다.

다행인건 역활이 안 바뀌었다면 난 아직도 혼자서 구글링을 하루에 5시간씩 했겠지. 

그리고 주제 2개정도 잡았을려나?

어쨋던

이 20%가 중요하다. 나는 미슐랭 가이드 심사위원이 되어야 한다.

Claude Code가 코드를 가져오면, 나는 깐깐한 심사위원처럼 굴어야 한다.

"셰프, 여기 에러 처리가 짜네. try-catch 블록이 너무 많아."

"이봐, 여기 함수가 3% 정도 덜 익었는걸? 엣지 케이스 처리가 빠졌어."

"이 모듈에 테스트가 부족해. 커버리지를 95%까지 올려줘."

이런 식으로 계속 트집을 잡아야 한다. 노쇼하라는 게 아니다. 정말 좋은 시스템을 만들려면 까다로운 고객이 되어야 한다는 거다.

처음엔 Claude Code가 가져온 코드에 감탄했다. "와, 이렇게 빨리?" 하면서 그냥 받아들였다. 그 결과가 스파게티 코드 1만 줄이었다.

이제는 다르다.

"타임아웃 시나리오 10가지 더 고려해."
"새 소스 추가하는 데 5분 넘으면 안 돼."
"메모리 사용량이 100MB 넘으면 리팩토링해."

이렇게 요구하니까 Claude Code도 더 신중해졌다. 

처음부터 테스트 코드를 같이 작성하고, 엣지 케이스를 미리 고려하고, 성능 최적화까지 신경 쓴다.

## 복순이가 가르쳐준 것들

**바이브 코딩은 시작점이다.** 아이디어를 빠르게 구현하기엔 최고다. 하지만 시스템으로 발전시키려면 명세서가 필요하다.

**AI와의 협업에는 경계가 필요하다.** Claude Code는 훌륭한 요리사지만, 미슐랭 스타를 받으려면 까다로운 심사위원이 필요하다. 그게 바로 인간의 역할이다.

**완벽한 시스템보다 진화하는 시스템이 낫다.** 복순이는 여전히 불완전하다. 하지만 이제 개선이 쉬워졌다. 새로운 요구사항이 생겨도 두렵지 않다.

**중복은 악이지만, 때론 필요악이다.** 처음엔 중복이 있어도 된다. 작동하는 게 우선이다. 나중에 패턴이 보이면 그때 리팩토링하면 된다.

## 복순이의 다음 도전

이제 복순이는 안정적으로 돌아간다. 매일 아침 500개의 콘텐츠를 수집하고, 50개의 고품질 콘텐츠를 선별한다.

다음 목표가 생겼다.

**복순이끼리 대화하게 만들기.** 복순이1이 찾은 AI 도구를 복순이5가 직장인 관점에서 평가하면 어떨까?

**자가 학습 시스템.** 내가 실제로 읽은 콘텐츠를 학습해서 취향을 파악하게 하고 싶다.

**실시간 알림.** 정말 중요한 뉴스가 나오면 즉시 알려주는 기능. 배치 처리가 아닌 이벤트 기반으로.

## 마무리: 스파게티에서 시스템으로

복순이는 바이브 코딩으로 태어났다. "대충 이런 느낌으로"라는 마음으로 시작했다.

스파게티 코드가 되었고, 매일 문제를 일으켰다. 하지만 포기하지 않았다. 

Spec Kit으로 명세서를 만들고, 체계적으로 리팩토링했다.

이제 복순이는 시스템이다. 예측 가능하고, 확장 가능하고, 유지보수 가능한.

바이브 코딩이 나쁜 건 아니다. 시작하기엔 최고의 방법이다. 

하지만 거기서 멈추면 안 된다. 명세서를 쓰고, 구조를 잡고, 시스템으로 진화시켜야 한다.

그리고 무엇보다 중요한 건, AI 시대에 개발자의 역할이 바뀌었다는 거다. 우리는 더 이상 코드를 치는 사람이 아니다. 미슐랭 심사위원처럼 품질을 관리하고, 방향을 제시하고, 까다롭게 요구하는 사람이다.

AI와 함께 일하는 시대다. Claude Code 같은 도구가 있으면 누구나 복순이 같은 시스템을 만들 수 있다. 중요한 건 시작하는 것, 그리고 계속해서 "이건 좀 아닌데?" 하고 트집 잡는 것이다.

복순이는 오늘도 열심히 일한다. 나보다 부지런하고, 나보다 꼼꼼하게.

그리고 나는 복순이가 가져온 콘텐츠를 보며 또 트집을 잡는다. 

"이봐 복순이, 오늘 콘텐츠 질이 좀 떨어지는데?"
