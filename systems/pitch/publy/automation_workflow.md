# 상세페이지 자동화 워크플로우(친절한 버전)

- 작성일: 2026-02-28
- 목표: "상세페이지를 AI로 100% 자동화"를 실제로 굴릴 수 있게, 단계/역할/산출물을 고정해서 만든다.
- 전제: 100% 자동화는 "사람은 최종 승인만"을 의미한다. (법무/표기 리스크 때문에 승인 단계는 남긴다.)

## (중요) 이 문서와 현재 구현의 관계

- 이 문서는 “개념을 친절하게 설명”한 버전입니다.
- 이 레포에서 **실제로 동작하는 구현**은 `publy_april_pitch/automation_kit/` 기준입니다.
- 실제 산출물 파일명은 `prompts/00_orchestrator.md`의 **번호(prefix) 규칙**을 따릅니다.

## 0) 한 줄 요약

AI에게 “그냥 알아서 만들어줘”라고 시키면 망가집니다.  
대신, `입력(한 장) → 단계별 결과물 → 템플릿 채우기 → 검사(게이트)`로 공장처럼 만들면 자동화가 됩니다.

## 1) 먼저 정해야 하는 3가지

1. 지금 목표는 “최종”인가, “초안+디벨롭”인가?
- 기획/디자인/사진이 거의 없는 상태라면 보통 “초안+디벨롭”이 목표입니다.
- 초안 단계의 결과물은 “최종 시안”이 아니라 아래 4개면 충분합니다.
  - 섹션 기획표(무슨 말을 어디에 쓸지)
  - 카피 초안(문장 묶음)
  - 와이어프레임(대충 배치)
  - 다음에 찍어야 할 사진 리스트(샷리스트)
- 마켓/자사몰이 아직 정해지지 않아도 괜찮습니다. 초안은 `HTML/CSS`처럼 중립 형태로 먼저 만들어두면, 나중에 어디든 옮기기 쉽습니다.

2. “자동화 완료”의 기준은 무엇인가?
- 추천: “사람은 마지막에 OK만 누른다”

3. 절대 지켜야 하는 규칙은 무엇인가?
- 예: 금칙어, 과장표현 금지, 필수 고지(배송/교환/환불), 톤앤매너

## 2) 용어를 쉽게 정리하면

- `SSOT(단일 진실 문서)`: 제품 정보를 **한 장**에 모아둔 것. 여기만 믿고 나머지는 복사해서 씀.
- `에이전트`: 역할을 나눠서 일하는 AI “팀원”.
- `템플릿`: 빈칸이 있는 “틀”. 빈칸만 채우면 결과물이 나온다.
- `품질 게이트`: 통과해야 하는 체크리스트. 여기서 걸리면 다시 고친다.

## 3) 전체 흐름(그림)

SSOT(제품/브랜드/제약)
  -> Intake(입력 점검)
  -> Questions(다음 루프용 질문)
  -> Planner(섹션 기획)
  -> Copy(카피 A/B)
  -> Design(블록 와이어프레임 + 컬러)
  -> Image(보정/보조 이미지 프롬프트 + 샷리스트)
  -> QA(금칙/근거/길이/필수고지 검사)
  -> 요약(run_summary)
  -> (선택) Renderer(HTML/Pencil/CMS 변환)
  -> 최종 승인(사람)

## 4) 가장 중요한 것: SSOT(제품 한 장) 만들기

AI 자동화에서 제일 흔한 실패는 “입력 정보가 흩어져 있거나 비어 있는 것”입니다.  
그래서 **무조건 한 장**으로 시작합니다.

예시(형식은 YAML/JSON 아무거나 OK):

```yaml
product:
  name: ""
  one_liner: ""
  price: ""
  usp: ["", ""]
  proof: ["인증/수치/후기 근거", "링크/이미지 위치"]
  faq: ["", ""]
brand:
  tone: "친절/단정/전문"
  must_include: ["배송/교환/환불", "주의사항"]
  forbidden: ["최고", "100% 보장", "무조건", "완치"]
page:
  target: "AI로 결과물을 빠르게 뽑고 싶은 마케터·기획자"
  platform: "HTML|CMS|이미지|디자인"
  sections: ["Hero", "USP", "Proof", "FAQ", "CTA"]
```

실제 템플릿 파일은 `publy_april_pitch/automation_kit/ssot_template.yaml`을 참고하세요.

규칙 하나:
- **근거 없는 말은 쓰지 않는다.** 근거가 없으면 “TODO”로 남긴다.

## 4-1) 제품만 덜렁 있을 때(자료 0) SSOT를 채우는 법

“사과/헤드폰/폼보드가 책상 위에 있고, 기획도 없고, 사진도 대충 찍은 것뿐”이어도 시작할 수 있습니다.  
핵심은 **사실(Fact)**, **추정(Guess)**, **질문(Question)**을 섞지 않는 것입니다.

- Fact(사실): 지금 눈으로 확인 가능한 것만
  - 예: 크기, 재질, 구성품, 색상, 포장 문구, 모델명, 무게(대략)
- Guess(추정): 아직 모르지만 “그럴 수 있다” 수준의 아이디어
  - 예: “이건 선물용으로도 좋아 보인다”
- Question(질문): 결정을 위해 반드시 확인해야 하는 것
  - 예: 가격, 타겟, 보장/AS, 배송 방식, 인증 유무

초안 자동화는 Fact로만 돌아가도 됩니다.  
대신 Question을 리스트로 뽑아 “다음 10분”에 채우면 2차 초안이 급격히 좋아집니다.

## 5) “AI 에이전트 팀”을 실제로 나누는 방법

중요 포인트는 “역할”과 “결과물 파일”을 고정하는 겁니다.

### 5-1) Intake Agent (입력 점검 담당)

- 하는 일: SSOT에 빈칸/모순/위험 문구가 있는지 체크
- 결과물: `01_intake_report.md`, `02_questions_to_answer.md`
- 통과 기준:
1. 가격/혜택/제약조건이 비어있지 않음
2. 주장(효과/수치)에 근거가 있음

### 5-2) Planner Agent (기획 담당)

- 하는 일: 섹션별 “무슨 말을 해야 하는지” 계획 세우기
- 결과물: `03_section_plan.json`
- 예:
  - Hero: 한 줄 가치 + 핵심 혜택 3개
  - Proof: 근거(인증/수치/후기)만 모아서 배치

### 5-3) Copy Agent (카피 담당)

- 하는 일: 섹션별 문장 만들기(버전 2개씩)
- 결과물: `04_copy_deck.md`
- 통과 기준:
1. 톤이 일관됨
2. 금칙어/과장표현 없음
3. 문장 길이 제한(모바일 기준) 지킴

### 5-4) Design Agent (배치/톤 담당)

- 하는 일: “어디에 무엇을 놓을지” 규칙을 글로 만든다
- 결과물: `05_wireframe.md`, `06_colors.json`
- 예:
  - 이미지 슬롯: 3개
  - 한 섹션당 텍스트는 3줄 이하
  - CTA 버튼 문구 12자 제한

### 5-5) Image Agent (이미지/샷리스트 담당)

- 하는 일:
  - 제품 사진 보정/보조 이미지 프롬프트 만들기
  - 다음 루프에서 찍을 사진(샷리스트) 뽑기
- 결과물: `07_image_prompts.md`, `08_shot_list.md`

### 5-6) Renderer Agent (템플릿 채우기 담당, 선택)

- 하는 일: 템플릿에 카피/이미지를 꽂아서 결과물을 만든다
- 결과물: `output/` 폴더(HTML, 이미지, 블록 등)

### 5-7) QA Agent (검수 담당)

- 하는 일: 결과물이 규칙을 어겼는지 자동 검사하고, 고치라고 피드백한다
- 결과물: `09_qa_report.md`
- 체크리스트 예:
1. “근거 없는 주장”이 섞였는가?
2. 필수 고지가 빠졌는가?
3. 길이 제한을 넘었는가?
4. 톤이 튀는가?

### 5-8) Summary Agent (요약 담당)

- 하는 일: 이번 실행의 결론과 다음 루프 TODO를 15줄 내로 요약
- 결과물: `run_summary.md`

## 6) 자동화 워크플로우를 “만드는” 순서(현업형)

처음부터 다 자동화하려고 하면 100% 깨집니다.  
대신 아래 순서로 “단단한 뼈대”부터 만들면 됩니다.

1. 지금 하는 일을 6단계로 쪼개서 적는다(기획/카피/배치/렌더링/QA/승인)
2. SSOT와 결과물 포맷을 고정한다(파일 이름까지 고정)
3. 렌더링(템플릿 채우기)부터 자동화한다
4. QA(검사)를 붙여서 “망가져도 자동으로 잡히게” 만든다
5. 마지막에 API 연동(노션/시트 입력 읽기, 결과 내보내기)을 붙인다
6. 프롬프트/템플릿 버전 관리(언제 바뀌었는지 기록)까지 넣는다

## 6-1) 추천 폴더 구조(한 번만 만들면 편해짐)

자동화를 “반복”하려면, 파일이 늘어나도 헷갈리지 않게 폴더를 나눠두는 게 좋습니다.

```
detail_page_draft_factory/
  ssot.yaml
  automation_kit/
    prompts/00_orchestrator.md
    rag/
      sources/
      scripts/
      index.json
    prompt_bundle.md
  runs/
    YYYYMMDD_HHMMSS_<product_slug>/
      01_intake_report.md
      02_questions_to_answer.md
      03_section_plan.json
      04_copy_deck.md
      05_wireframe.md
      06_colors.json
      07_image_prompts.md
      08_shot_list.md
      09_qa_report.md
      run_summary.md
  # (선택) output/  -> HTML/CMS/Pencil 변환 결과
```

핵심은 2가지입니다.
- `ssot.yaml`만 바꾸면 같은 워크플로우로 다른 상품도 만들 수 있어야 함
- `output/`는 “최종 결과물만” 나오게 해서 찾기 쉽게 함

## 6-2) Claude Code와 API는 어디에 쓰는가?

쉽게 말하면:
- `Claude Code`는 “팀장” 역할입니다. (각 에이전트에게 일을 시키고 결과물을 파일로 저장하게 함)
- `API`는 “자동으로 자료를 가져오고/내보내는 전화선”입니다.

예시로 보면:
1. API로 노션/시트에서 제품 정보를 읽어서 `ssot.yaml`을 채운다
2. Claude Code가 `01_intake -> 02_plan -> 03_copy ...` 순서대로 실행한다
3. 결과물이 `output/`에 나오면 API로 CMS(상세페이지 에디터)나 스토리지에 업로드한다

## 6-3) 초안 -> 디벨롭 “반복 루프” (가장 현실적인 자동화)

처음부터 완벽한 페이지를 만들려고 하면 늦고 스트레스만 쌓입니다.  
대신 아래처럼 “짧게 여러 번” 돌리는 게 정시 퇴근에 더 가깝습니다.

1. 1차(10~30분): Fact만으로 초안 만들기
- 섹션 기획표 + 카피 초안 + 와이어프레임 + 샷리스트까지

2. 2차(10~30분): Question 5개만 답하고 다시 만들기
- 가격/타겟/한 줄 USP/필수 고지/제약조건 정도만 채워도 품질이 확 올라감

3. 3차(10~30분): 핸드폰 사진 3장만 더 찍고 다시 만들기
- “정면 1장 + 디테일 1장 + 사용 상황 1장”만 추가해도 설득력이 크게 개선됨

이 루프가 자동화의 핵심입니다.  
최종 시안은 마지막에 필요할 때만 다듬으면 됩니다.

## 7) Figma vs pencil.dev: 뭐가 더 나을까?

결론부터 말하면:
- “혼자 빨리 자동화”가 목표면 `pencil.dev`가 유리합니다(이미 쓰고 있으니까).
- “다른 사람과 협업/공유”가 목표면 `Figma`가 유리합니다(업계 표준에 가깝습니다).

### Figma가 유리한 상황

- 디자이너/팀원이 이미 Figma로 협업한다
- 결과물을 클라이언트/외부와 공유해야 한다
- 디자인 리뷰(코멘트/버전)를 많이 한다

### pencil.dev가 유리한 상황

- 내가 이미 사용 중이라 러닝커브가 낮다
- “AI로 빠르게 생성 → 수정 → 다시 생성”을 반복한다
- 결과를 최종적으로 `HTML`이나 `이미지`로 뽑아 배포한다

### 추천(지금 상황 기준)

- 본문 워크플로우는 “툴 중립”으로 설명하고,
  - 출력은 `HTML/CSS` 또는 `에디터 블록`처럼 누구나 이해하는 형태로 잡는다.
- 디자인 도구 파트는 “선택”으로 두고,
  - 나는 `pencil.dev` 트랙을 예시로 보여주되,
  - 독자를 위해 “Figma로도 원리는 같다(템플릿+검수+승인)”라고 안내한다.

## 8) 글에 넣기 좋은 데모(독자 설득용)

- 같은 SSOT로
1. 자동화 전: 사람이 3시간 걸리던 상세페이지
2. 자동화 후: 사람은 10~20분 검수만
- 그리고 “어디서 시간이 줄었는지”를 단계별로 보여주기

## 9) 안전장치(진짜 중요)

- 성능/효과/수치/인증은 **근거 없으면 쓰지 않는다**
- 민감정보(고객 데이터/매출 원본)는 SSOT에 넣지 않는다
- QA 게이트에서 걸리면 “자동 수정 1회 + 사람 최종 확인”을 원칙으로 둔다

3. 섹션 템플릿 5개(Hero/USP/Proof/FAQ/CTA) 만들기
4. QA 체크리스트 15개 만들기(금칙어/필수고지/근거/길이)
