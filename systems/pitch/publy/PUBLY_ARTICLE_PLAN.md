# 퍼블리 원고 계획: 상세페이지 “초안 공장” (복붙 vs 자동화)

- 작성일: 2026-03-01
- 원고 주제(테마 1-1): **클로드 코드로 상세페이지 100% 자동화하기: 나만의 AI 에이전트 팀 구축법**
- 독자: AI로 결과물을 빨리 뽑고 싶은 **마케터/기획자**
- 원고 목표: “상세페이지를 잘 쓰는 법”이 아니라 **반복 생산 라인(시스템)**을 만드는 법
- Intent SSOT: `00-INTENT.md`

---

## 0) 한 줄 약속(원고 첫 문단용)

“제품만 책상 위에 있어도, 30분 안에 `기획 + 카피 + 와이어프레임 + 샷리스트 + QA` 초안을 한 세트로 뽑고, 같은 방식으로 계속 찍어내는 시스템을 만듭니다.”

---

## 1) 원고에서 보여줄 2가지 트랙

원고는 **둘 다** 보여주고, 독자가 상황에 맞게 고르게 한다.

### Track A: 복붙(노코드) — “오늘 당장 1회성으로” 돌리는 방법

핵심: 도구 소개가 아니라 **산출물 계약(파일 10개)**을 고정한다.

- 입력: `ssot.yaml`
- 실행: Claude Code에 `prompts/00_orchestrator.md`를 그대로 붙여넣고 실행
- 출력: `runs/YYYYMMDD_HHMMSS_<product_slug>/` 아래 10개 파일

독자에게 주는 가치:
- 세팅 거의 없이 바로 됨
- “무엇을 만들어야 하는지”부터 정리된다(초안 세트)

원고에 넣을 것(필수):
- SSOT 최소 예시 1개(빈칸 많아도 OK)
- 1차 결과물 일부 캡처(특히 `02_questions_to_answer.md`, `05_wireframe.md`, `08_shot_list.md`)

### Track B: 스크립트/자동화 — “계속 만들” 시스템으로 굳히는 방법

핵심: 매번 품질이 흔들리는 문제를 **작은 RAG(규칙 묶음)**로 잡고, 실행 전에 자동 주입한다.

- 입력: `ssot.yaml` + 작은 RAG(`rag/sources/*.md`)
- 준비: `node scripts/build_index.mjs`로 인덱스 생성
- 실행: `node scripts/make_prompt_bundle.mjs`로 `prompt_bundle.md` 생성 -> Claude Code에 붙여넣고 실행
- 출력: Track A와 동일 + (간접효과) 톤/규칙/QA가 더 안정적으로 적용됨

독자에게 주는 가치:
- 팀/반복 작업에서 “매번 흔들림”이 줄어든다
- 실패가 나도 “룰을 추가하면 다음 실행에서 바로 고쳐짐”

원고에 넣을 것(선택/권장):
- “왜 RAG가 필요한가”를 3문장으로만 설명(길게 금지)
- 2차 실행에서 개선된 결과 1개 비교 캡처(예: 금지 표현이 사라짐, 정책 TODO 템플릿 자동 삽입)

---

## 2) 장단점 비교표(원고 중간에 그대로 삽입)

| 항목 | Track A: 복붙(노코드) | Track B: 스크립트/자동화 |
|---|---|---|
| 시작 속도 | 매우 빠름(5~10분) | 느림(30~60분, 1회 세팅) |
| 재현성(같은 품질) | 중간: 프롬프트/기억에 의존 | 높음: 룰(RAG)로 고정 |
| 유지보수 | 거의 없음 | 문서/룰 업데이트 필요 |
| 팀 공유 | 낮음(사람마다 다르게 실행) | 높음(룰/템플릿 공유) |
| 실패 복구 | “그때그때” 감으로 수정 | “룰 추가 → 다음 실행 자동 개선” |
| 추천 상황 | 1~2개 빠르게 뽑을 때 | 월/주 단위로 계속 찍어낼 때 |

결론 문장(원고용):
- “1번 해볼 땐 Track A가 이깁니다. 하지만 3번부터는 Track B가 이깁니다.”

---

## 3) 원고 목차(추천)

퍼블리 문체에 맞춰 “설명”보다 “실행” 중심으로 간다.

1. 문제 공감: 상세페이지가 왜 매번 ‘처음부터’인지
2. 10분 요약: 오늘 얻는 결과물 10개(파일 목록)
3. Track A(복붙): 제품만 있을 때 30분 1차 초안 만들기
4. Track A의 한계: 왜 두 번째부터 흔들리는가(3가지)
5. Track B(자동화): 작은 RAG로 흔들림을 고정하는 법
6. 실패/복구: 결과물이 맘에 안 들 때 고치는 순서(트러블슈팅)
7. 1주 적용 플랜: “1차-2차-3차 루프”로 운영하기
8. 부록: SSOT 템플릿 + 복붙 프롬프트 + QA 체크리스트

---

## 4) 데모 준비(원고의 “증거” 만들기)

원고 신뢰도는 데모가 좌우한다. 최소 1개 제품만으로도 충분하다.

### 데모 시나리오(최소)

1. SSOT 거의 비움(팩트만) -> 1차 실행
2. 질문 5개만 답함(가격/타겟/정책/제약/한 줄 USP) -> 2차 실행
3. Track B로 동일 제품 1회 실행 -> 규칙이 자동 반영되는 캡처 1장

### 캡처 후보(원고에 넣기 좋은 것)

- `02_questions_to_answer.md`: “다음에 뭘 채우면 좋아지는지”가 한눈에 보임
- `05_wireframe.md`: 비디자이너도 ‘페이지가 보이는’ 순간
- `08_shot_list.md`: 사진이 없어도 다음 루프가 생김
- `09_qa_report.md`: 과장/근거/필수고지를 자동으로 잡는 부분
