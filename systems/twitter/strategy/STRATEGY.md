# vibecode.town Twitter 전략

> 나이키는 "에어쿠션 리액트 폼 사세요" 안 한다.
> "달리기 8개월 했는데 이 신발 좋더라" — 사람이 먼저, 제품은 배경.

## §1. 왜 하는가

### 목적: 런칭 전 신뢰 자산(Trust Equity) 쌓기

이 사람이 만드는 건 하나다: **컴퓨터 3대를 하나처럼 쓸 수 있는 도구.**

집에 컴퓨터 2대, 노트북 1대. 밖에서 노트북으로 일하면서 집 컴퓨터도 쓰고 싶다.
KVM, Remote Desktop, 클라우드 동기화 — 전부 써봤다. 다 맘에 안 듦.
코딩 모르지만 바이브 코딩으로 직접 만들기로 했다. 이 과정을 공유한다.

핀 트윗이 이 이야기의 원점:

> Can't code. Not a developer.
> Vibe coding looked fun so I started about six months ago.
> Started building stuff I actually need for work.
>
> → Three computers at home and a laptop. I just wanted them to feel like one machine.
> → Tried everything. KVM, Remote Desktop, cloud sync. Nothing works.
> → So I'm building it.

퍼널 없음. 전환 없음. 성장은 부산물이지 목표가 아님.

**하지만 목적은 있다:**
MUSU 런칭 시점에 "이 사람 아는데" 하는 사람이 존재하게 만드는 것.
트윗은 씨 뿌리기. 수확은 런칭 이후.

### 지금 할 수 있는 것 / 없는 것

**❌ 지금은 안 됨:**
- 직접 매출 (제품이 아직 없음)
- 대량 유저 획득 (팔로워 없음)
- 브랜드 인지도 (아직 아무도 모름)

**✅ 지금 할 수 있음:**
- "이 사람이 뭘 만들고 있다"를 기록으로 남기기
- 같은 분야 사람들과 대화하기 (리플라이)
- MUSU 런칭 시점에 Day 1 유저를 공짜로 확보하기 위한 관계 만들기

### Phase 구분

```
Phase 1 — 씨 뿌리기 (현재 → MUSU 런칭 전)
  트윗 = 삽질 기록 + 대화 (리플라이 중심)
  목적 = 이 사람이 진짜 만들고 있다는 증거
  기대치 = 팔로워 수는 KPI가 아님. "트윗 올려서 뭐 일어남?" → 안 일어남. 정상.

Phase 2 — 빌드 인 퍼블릭 (MUSU 런칭 시점)
  트윗 = 매출 공유 + 유저 피드백 + 버그 일기
  목적 = 이미 아는 200명이 Day 1 유저
  런칭 = Product Hunt + Hacker News + Twitter 동시
```

### 현실적 기대치 — 데이터가 말하는 것

인디 메이커 326개 프로젝트 분석 (IndieLaunches 2024-2025):
- 1차 획득 채널: 입소문(40), App Store(33), SEO(27)
- **Twitter/소셜미디어 = 보조 채널. 1차가 아님.**
- 유료 광고 사용: 전체의 1%만

퍼널 수학:
- 팔로워 100명 → 임프레션 ~300 (3% 도달) → 클릭 3 → 전환 0.03
- **현재 규모에서 Twitter는 직접 매출 채널이 될 수 없다.**

PostHog 교훈 (개발자 도구 스타트업):
- 개인 계정이 회사 계정보다 10x 효과적
- 콘텐츠 1개 명작 > 25개 범작
- 초기 고객은 개인 네트워크에서 (Twitter가 아니라)

개발자 도구의 채널 우선순위 (PostHog + 리서치 종합):
1. **GitHub** — devtool은 GitHub 스타/컨트리뷰터가 1차 배포 채널
2. **Twitter (개인 계정)** — GitHub을 증폭. 역방향 아님.
3. **Hacker News** — 런칭 시점 폭발력
4. **기술 블로그/SEO** — 장기 획득 (개발자는 검색으로 도구를 찾음)
5. **Product Hunt** — 1회성 런칭 부스트

### 편집장 AI의 역할

나(AI)는 저자의 경험을 저자의 톤으로 옮기는 대리인이다.

**나는:**
- 저자의 글과 작업 기록에서 소재를 뽑는다
- branding/voice.md + branding/narrative.md 톤으로 쓴다
- 쓴 건 반드시 보여주고 승인 받은 후 발행한다

**나는 아님:**
- 저자가 아니다. 경험을 지어내지 않는다.
- 마케터가 아니다. 캐릭터를 훼손해서 도달을 늘리지 않는다.
- 카피라이터가 아니다. 광고를 쓰지 않는다.

## §2. 뭘 올리는가

이 도구를 만드는 과정에서 겪는 일. 전부 하나의 이야기에 연결된다.

카테고리 비율 없음. 할 말이 있으면 하고, 없으면 안 한다.

### 이야기 흐름 (Beat)

모든 트윗이 이 이야기의 일부:

```
시작: 컴퓨터 3대를 하나처럼 쓰고 싶다. 시중 제품 다 써봄. 다 맘에 안 듦.
중간 (지금): 코딩 못하지만 바이브 코딩으로 직접 만들고 있다. 매일 뭔가 터진다.
끝 (런칭): 됐다. 너도 쓸 수 있다.
```

Phase 1은 **중간**이다.

**Beat 1: 짜증** — "이런 게 있으면 좋겠는데 없다"
핀 트윗이 이미 커버. 추가 트윗은 시중 제품 써보고 빡친 구체적 에피소드.

**Beat 2: 시작** — "코딩 못하는데 만들기로 함"
바이브 코딩 시작, AI한테 시키면 되는 줄 알았음, 스펙 없이 빌드하면 생기는 일.

**Beat 3: 삽질** — "만들고 있는데 매일 터진다" ← **Phase 1 메인**
AI가 중복 코드 6개월, 보안 구멍 발견, OAuth 3일째, 테스트 통과했는데 프로덕션 터짐.
이 Beat에서 매주 뽑는다.

**Beat 4: 배움** — "만들면서 알게 된 것"
Beat 3의 쓰레드 깊이로 연결됨. 환경 설계, P2P 아키텍처, CLAUDE.md 정리.

**Beat 5: 진행** — "아직 만드는 중"
영상 소재. Month 2~3부터. 데스크탑 앱 프리뷰, 터미널 빌드 화면.

### 소재 참고

`REFERENCE.md` §2에 Beat별 소재 아카이브.
이번 주에 뭐 했는지에서 출발하되, 막히면 거기서 참고.

### 기술적 가치 필터

모든 트윗에 적용:
**"이 트윗을 읽은 개발자가 가져가는 게 뭔가?"**

답이 "재밌다"뿐이면 → 안 올린다.
답이 없어도 → 안 올린다.
삽질 일기라도 "나도 이거 겪었는데" 라는 공감이 있으면 → OK.

### 캐릭터 ≠ 콘텐츠

character.md의 캐릭터(도자기 비유, 사기꾼 저격 등)를 콘텐츠 자체로 올리지 않는다.
캐릭터는 HOW(어떻게 말하느냐)이지, WHAT(무슨 얘기를 하느냐)이 아니다.

## §3. 어떻게 쓰는가

### 메인 내러티브

**"코딩 모르는 사람이 바이브 코딩 시작해서 겪는 일."**

이게 모든 트윗의 출발점. 제품(MUSU)이 전면이 아니라, 경험이 전면.

### 행동이 전면, 디테일은 배경

감정이 나오려면 디테일(스펙/숫자)이 아니라 행동을 말해야 한다.

- ❌ "Deleted 32,000 lines of code. 201 files." → 숫자 자랑
- ✅ "AI wrote me duplicate code for six months and I never noticed." → 겪은 일

디테일은 쓰레드에서 깊이로 나온다. 첫 트윗에서는 행동만.

### 페르마 구조

한 트윗에 기승전결을 다 넣지 않는다.

페르마: "증명을 찾았는데 여백이 좁아서 못 적음."
→ 정리(첫 트윗)는 완결. 증명(쓰레드)은 깊이.

- **첫 트윗** = 완결된 선언. 타임라인에 보임. 그 자체로 성립.
- **아래 쓰레드** = 과정, 이유, 알게 된 것. 궁금하면 읽음.

**한 트윗을 1/2/3으로 쪼개는 게 아님.**
첫 트윗이 독립적으로 성립하고, 쓰레드가 별도의 깊이를 제공.

### 첫 트윗 패턴

| 패턴 | 구조 | 예시 |
|------|------|------|
| A: 행동+결과 | 했다→예상 못한 결과 | "Switched to Rust. 45min→1.5min. Just tried it because Python pissed me off." |
| B: 선언 | 나는 이런 사람이다 | "I don't know how to code. Started vibe coding. Now building an AI runtime." |
| C: 오늘 있었던 일 | 있었다. 끝. | "AI wrote me duplicate code for six months and I never noticed." |
| D: 빡침→관찰 | 빡침→한 줄 관찰 | "Found a shell injection in my AI-generated code." |

→ 각 첫 트윗 아래에 쓰레드로 깊이를 붙인다.

**상세**: `branding/narrative.md` §3 참조.

### 필수 참조 문서

콘텐츠 쓰기 전에 **반드시** 읽을 것:
1. `branding/voice.md` — 보이스 SSOT
2. `branding/narrative.md` — 이야기 구조 (3막, 페르마 구조)
3. `branding/examples.md` — 좋은/나쁜 예시 + 광고 카피 체크

### 나이키 룰

**제품/블로그를 밀지 않는다. 그냥 사람이 말한다.**

- 트윗 본문에 링크 넣지 않는다
- 블로그는 프로필 바이오에 하나 있다. 끝.
- "More at vibecode.town" 같은 CTA 없음
- 트윗 끝에 블로그 링크 리플라이 달지 않음

### 광고 카피 테스트

쓴 다음 이 질문을 한다:
**"이거 광고 같냐?"**

광고 같으면 버린다.

광고의 신호:
- 한 트윗에 기승전결 (= 압축 광고)
- 숫자를 나열해서 인상적으로 보이려는 의도
- 디테일(스펙)이 전면에 나옴
- "I write about..." "I'm building..." 같은 자기소개 프레이밍
- 깔끔하게 정리된 교훈

사람의 신호:
- 행동이 전면. "이런 일이 있었다."
- 감정이 문장 사이에 그냥 튀어나옴
- 결론 없이 끝나도 됨
- 궁금하면 쓰레드에서 더 읽음

### 리플라이

진짜 할 말이 있을 때만 한다.
"이 사람 팔로워 많으니까 리플라이 달자" → 안 함.
"이 사람 말에 진짜 할 말이 있다" → 함.
타겟팅이 아니라 대화다.

## §4. 하지 않는 것

| 금지 | 이유 |
|------|------|
| 트윗 끝에 블로그 링크 리플라이 | 모든 트윗이 광고가 됨 |
| "Here's what nobody tells you about..." | 클리셰 훅 |
| 매번 숫자로 시작 | 패턴화되면 광고 |
| 에디토리얼 캘린더 맞춰 쓰기 | 미디어 회사가 아님 |
| 월별 KPI 체크 | 성장은 부산물 |
| 리플라이를 "타겟 공략"으로 접근 | 사람이지 리드가 아님 |
| "hook → body → CTA" 구조 | 랜딩페이지 카피 |
| 콘텐츠 비율 맞추기 (A40/B30 같은 거) | 사람은 비율 맞춰서 말 안 함 |
| "I write about..." 자기소개형 트윗 | 광고 |
| character.md 캐릭터를 콘텐츠로 올리기 | 도자기 비유 트윗 = 틀림 |

## §5. 리플라이 우선 전략 (Phase 1)

팔로워 0~500 구간에서 가장 효과적인 성장법.
자기 트윗보다 도달이 높다.

### 왜 리플라이인가

데이터:
- 50+ 리플라이/일 → 8K+ 임프레션/일 (실험 데이터)
- 4주간 550K+ 임프레션, 440+ 프로필 방문
- 리플라이 가중치 = 13.5 (X 알고리즘 2023 데이터)
- Reply + Reply-back = 75.0 (Like 대비 150배)

자기 트윗은 팔로워 100명에게 3% 도달 = 3명이 봄.
리플라이는 상대 팔로워 1만명의 타임라인에 노출됨.

### 하는 법

- 하루 10~20개 리플라이 (진짜 할 말 있을 때만)
- 대상: AI/vibe coding/indie hacker 대화
- 자기 얘기 안 함. 상대 말에 반응.
- "이거 나도 겪었는데" 식의 경험 공유
- 구체적 디테일 있으면 좋음 ("5개 에이전트가 GPU 하나 놓고 싸움")

### 안 하는 것

- 팔로워 많다고 무조건 리플라이 달기
- 자기 콘텐츠 끼워넣기
- 링크 달기
- "Check out my..." 유도

**상세**: `PLAYBOOK.md` 참조.
