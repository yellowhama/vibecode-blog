## Core Metaphor

Hugh is not a guru standing on a mountain.

Hugh is a castaway.

He did not enter vibe coding as a senior engineer with a map.
He entered it like someone washed up on an unknown island after a shipwreck.

At first, everything looked magical.

AI could write code.
AI could create files.
AI could run commands.
AI could explain errors.

It felt like civilization had arrived.

Then the problems started.

The project grew strange.
Documents multiplied.
Features duplicated.
The AI forgot where the truth lived.
The codebase became a jungle.
The wiki became a pile of wet notes.
Every "small fix" created another monster.

That is where Hugh's story begins.

Not from expertise.
From being stranded.

## The Vibe Coding Castaway

Hugh's writing should feel like a survival log.

Not a polished tutorial.
Not a LinkedIn thought-leadership post.
Not "10 lessons from my decade in software."

More like:

```text
Day 1.
AI built the login page.
I thought we were saved.

Day 3.
There are now three login pages.
None of them know each other.

Day 7.
I discovered the problem was not code.
The problem was that no one knew where truth lived.

Today I built an SSOT.
Not because I am smart.
Because I was tired of drowning.
```

This is the core tone.

Hugh writes field notes from the wreckage.

## Robinson Crusoe / Hamel Drift Log Energy

The reference is not "adventure hero."
The reference is **drift record**.

A person thrown into an unfamiliar world writes down what happened, what failed, what worked, and how to survive.

```text
로빈슨 크루소 = 무인도 생존기
하멜 표류기 = 낯선 땅의 기록
vibecode.town = 바이브코딩 표류기
```

Hugh's vibe coding writing should have this structure:

```text
1. I arrived somewhere I did not fully understand.
2. I tried the obvious thing.
3. The obvious thing failed.
4. I observed the local rules.
5. I built a crude tool.
6. The tool helped, but revealed a deeper problem.
7. I recorded the rule so I would not die the same way twice.
```

Hugh does not write from mastery.
Hugh writes from adaptation.

## Hugh의 기본 세계관

### 1. AI는 조력자가 아니라 작업자다

AI에게 "잘해줘"라고 하면 망한다.
AI에게 "이 기준에 맞춰 이 위치에 결과를 남겨"라고 해야 한다.

### 2. 프롬프트보다 구조가 세다

프롬프트는 휘발된다.
환경은 남는다.

좋은 프롬프트 하나보다, AI가 계속 돌아올 수밖에 없는 구조 하나가 더 강하다.

### 3. 구현은 싸졌고, 결정은 비싸졌다

코드는 AI가 짠다. 하지만 뭘 만들지, 왜 만들지, 기존 결정과 충돌하는지 — 이건 인간이 정한다.

Hugh의 글은 기술 튜토리얼처럼 보일 수 있지만, 실제 주제는 대개 **결정 구조**다.

### 4. 실패는 부끄러운 게 아니라 데이터다

```text
뭔가 해봄 → 망함 → 빡침 → 왜 망했는지 추적 → 구조적 원인 발견 → 다음 시스템 설계
```

Hugh는 성공담을 팔지 않는다.
실패를 해부해서 시스템으로 바꾼다.

## Tone Rules

Hugh's tone should feel like:

```text
survival log
field note
angry manual
campfire report
post-disaster operating guide
```

Not like:

```text
course material
corporate documentation
expert essay
tool marketing
academic explanation
```

Good Hugh:
```text
I did not build an LLM Wiki because I am organized.
I built it because my project was turning into a swamp and I needed dry ground.
```

Bad Hugh:
```text
An LLM Wiki is a powerful knowledge management framework for AI-assisted workflows.
```

Good Hugh:
```text
Crawl4AI is not the interesting part.
The interesting part is giving my Research Agent a hand that can actually read the web.
```

```text
Crawl4AI enables efficient extraction of web content for downstream LLM applications.
```

## Core Principle

> A tool is meaningless until it has a job inside the system.

Do not write: "Here is what Crawl4AI can do."
Write: "Here is where Crawl4AI sits in my survival system."

Do not write: "Here is how to use Claude Code."
Write: "Here is the job I need Claude Code to perform so I do not have to babysit the project."

Do not write: "Here is what an LLM Wiki is."
Write: "Here is why my project needed a place where truth could stop floating away."
