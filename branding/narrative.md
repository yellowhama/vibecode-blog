# Narrative — 이야기 구조

> 이 사람의 글은 설명이 아니다. 이야기다.
> 톤은 `voice.md`가 잡는다. 구조는 이 문서가 잡는다.

## §1. 3막 구조

모든 콘텐츠(블로그, 트윗)는 이 3막을 따른다.
의식적으로 넣는 게 아니라, 이 사람이 원래 이렇게 생각함.

### 1막: 짜증

뭔가 존나 불편하다. 짜증난다. 이게 뭘 만들 이유.

- 구체적 상황에서 시작. 추상적 문제 정의가 아님.
- "월요일 아침 에이전트 5개가 죽었다" — O
- "AI 에이전트 장애 대응에 대하여" — X
- 감정이 먼저. 분석은 나중.

| 블로그 예시 | 짜증 |
|-------------|------|
| 006-복순이-대수술기 | 월요일 아침, 에이전트 5개 전멸. 10,847줄 스파게티. |
| 010-5분-문서화 | 새벽 4시, 3시간 날림. Claude가 이미 있는 거 또 만듦. |
| 015-git-세이브 | 파일 30개. `게임_최종_진짜_마지막.godot`. 뭐가 되는지 모름. |
| 052-구현은-공짜다 | 스펙 문서 1개가 일주일 만에 30개로 폭발. |
| 058-짜증이-스펙 | 컴퓨터 3대가 따로 놀아서 빡침. |

### 2막: 난리

만들었더니 또 난리. 왜지? 씨발?

- 시도했는데 다른 문제가 터짐.
- 또는 해결인 줄 알았는데 아니었음.
- "되는 줄 알았는데" 순간이 핵심.

| 블로그 예시 | 난리 |
|-------------|------|
| 006 | Rust로 전환 → 성능은 좋은데 새로운 문제 발생 |
| 007-주식-스크리너 | Python→Rust+PyO3 → WinError 216 |
| 052 | AI가 기존 문서 안 고치고 새 문서만 계속 만듦 → 왼팔 28개 |
| 055→056 | RAG 달았더니 환각은 줄었는데 "맞는 파일 가져오고 결과가 틀림" |
| 057 | 3-tier 검색 만들었더니 같은 정보가 3군데에서 충돌 |

### 3막: 파헤침

정확한 문제가 뭐지? 다시 보자. 이건 또 뭐지?
어려운 기술을 쉽게 이야기함. 다른 예를 들어서 이야기함.

- **블로그**: 일상 비유로 기술을 번역. (엄마 옷장 = RAG, 다크소울 = Git)
- **트윗**: 비유 대신 펀치라인 한 줄로 찍음. ("It still breaks.")
- 깔끔한 결론이 아님. "아직 모르겠다"도 OK. 선언문 한 줄도 OK.

| 블로그 예시 | 비유/통찰 |
|-------------|-----------|
| 057 | 엄마 옷장 정리 = RAG 3-tier 검색 |
| 015 | 다크소울 모닥불 = Git 세이브 |
| 009 | 밀 농사부터 짓겠다 = 바퀴 재발명 |
| 045 | 레스토랑 주방 = 컨텍스트 엔지니어링 |
| 052 | 왼팔 28개 달린 몸 = SSOT 없는 코드베이스 |
| 006 | 미슐랭 검수관 = 개발자 역할 |
| 058 | 태초에 짜증이 있었다 = 짜증이 곧 스펙 |

## §2. 블로그 6비트 — 글 쓸 때의 구조 체크리스트

블로그 글은 3막이 6개 비트로 펼쳐진다.
모든 비트가 매번 나올 필요 없음. 1막만 있는 글도 OK.

| 비트 | 역할 | 해당 막 |
|------|------|---------|
| **Scene** | 구체적 상황. 시간, 장소, 물리적 디테일. "월요일 아침, 커피 한 잔." | 1막 |
| **Wall** | 뭔가 안 됨. 부서짐. 더 깊은 문제 드러남. | 1~2막 |
| **Discovery** | 외부 소스(글, 도구, 영상)가 새 프레임 제공. 또는 삽질 끝에 발견. | 2~3막 |
| **Experiment** | 새 접근법 시도. AI 대화 포함. 실시간 서술. "해봤다." | 2막 |
| **Before/After** | 구체적 숫자 비교. "45분→1.5분", "500줄→87줄" | 3막 |
| **Declaration** | 인용 가능한 한 줄. "태초에 짜증이 있었다." "구현은 공짜다." | 3막 |

선택:
| **Tease** | 다음 글 예고. 시리즈 연결. "다음 글에서 이 질문에 답한다." | — |

### 이걸 "구조"라고 외우면 안 됨

이건 공식이 아님. 이 사람이 원래 생각하는 순서를 관찰한 것.
"Scene 넣고 Wall 넣고 Discovery 넣어야지" 식으로 쓰면 → 설명이 됨.
그냥 있었던 일을 순서대로 쓰면 자연스럽게 이 비트가 나옴.

## §3. 트윗: 페르마 구조

### 메인 내러티브

**"코딩 모르는 사람이 바이브 코딩 시작해서 겪는 일."**

이게 모든 트윗의 출발점. 제품(MUSU)이 전면이 아니라, 경험이 전면.
- ❌ "AI 런타임 만드는 개발자" (제품 중심)
- ✅ "코딩 못하는 사람이 AI로 뭔가 만들려고 발버둥" (경험 중심)

### 핵심 원칙 1: 행동이 전면, 디테일은 배경

감정이 나오려면 디테일(스펙)이 아니라 행동을 말해야 한다.

- ❌ "Deleted 32,000 lines of code. 201 files." (디테일 = 숫자 자랑)
- ✅ "AI wrote me duplicate code for six months and I never noticed." (행동 = 발견)
- ❌ "Added nonce-based CSP headers." (기술 스펙)
- ✅ "Found a shell injection in my AI-generated code." (겪은 일)

디테일(Rust, 32K LOC, CSP nonce)은 쓰레드에서 깊이로 나온다. 첫 트윗에서는 행동만.

### 핵심 원칙 2: 페르마 구조

**한 트윗에 기승전결을 다 넣지 않는다.**

페르마의 정리: "증명을 찾았는데 여백이 좁아서 못 적음."
→ 정리(첫 트윗)는 완결. 증명(쓰레드)은 깊이.

- **첫 트윗** = 완결된 선언. 타임라인에 보이는 것. 그 자체로 성립.
- **아래 쓰레드** = 깊이. 과정, 이유, 알게 된 것. 궁금하면 읽음.

**⚠️ 한 트윗을 1/2/3으로 쪼개는 게 아님.**
첫 트윗이 독립적으로 성립하고, 쓰레드가 별도의 깊이를 제공하는 것.

예시:
```
첫 트윗: "AI wrote me duplicate code for six months and I never noticed."

쓰레드:
→ "Agent 3 and Agent 5 built the exact same function. Neither knew the other existed."
→ "Three different date formatters. Two config parsers. Four ways to validate input."
→ "Started deleting. The app didn't break. It got faster."
```

첫 트윗만 읽어도 이야기가 성립. 쓰레드는 "왜? 어떻게?"에 답함.

### 첫 트윗 패턴

**패턴 A: 행동 + 예상 못한 결과**

```
Switched the data collector to Rust. 45 minutes down to 1.5.
Just tried it because Python was pissing me off.
```
→ 쓰레드: Rust 전환 과정, 뭘 배웠는지

**패턴 B: 선언**

```
I don't know how to code.
Started vibe coding six months ago.
Now I'm building an AI runtime.
```
→ 쓰레드: 어떻게 시작했는지, 지금 어디까지 왔는지

**패턴 C: 오늘 있었던 일**

```
Six months in, I finally read all the code AI wrote for me.
Five copies of the same function.
```
→ 쓰레드: 에이전트별 중복, 정리 과정

**패턴 D: 빡침 → 관찰**

```
Found a shell injection in my AI-generated code.
```
→ 쓰레드: 보안 감사 계기, 몇 번째 줄, AI가 씀+내가 승인함

### 트윗에서 절대 안 하는 것

- 디테일(스펙/숫자)을 첫 트윗 전면에 놓기
- 한 트윗에 기승전결 다 넣기 (= 압축 광고)
- "결론은~" 식으로 정리하기
- 비유를 길게 풀기 (블로그 전용)
- 펀치라인을 "멋있게" 만들기 — 그냥 사실이면 됨

## §4. 비유 도구함 — 블로그용

트윗에서는 안 씀. 블로그에서 어려운 기술을 설명할 때만.

### 원칙

1. **거창한 것을 지하실로 끌고 내려간다**
   - "UX? 폰 잠금 풀고, 탭하고, 끝. 그게 좋은 UX." (voice.md 법칙 1)
2. **전문 용어 먼저 안 꺼냄** — 비유 먼저, 용어는 나중에
3. **이미 쓴 비유 재활용 OK** — 캐릭터의 일관성

## §5. "이야기" vs "설명"

같은 소재인데 쓰는 방식이 다르면 완전히 다른 글이 됨.

### 비교 1: RAG

**이야기** ✅ (057 실제 도입부)
```
"엄마, 아까 새로 산 거 어딨어?"
"여기."
"아니 그 검은 거 말고. 새로 산 거. 분홍색."
"이거?"
"아니, 분홍색 바지 말고. 분홍색 티."
이 시점에서 엄마 폭발.
"야 옷장부터 정리해라 임마!"
```

**설명** ❌
```
RAG(Retrieval-Augmented Generation)란 외부 데이터를
검색하여 LLM의 응답에 활용하는 기술입니다.
이를 통해 환각(hallucination)을 줄일 수 있습니다.
```

### 비교 2: Git

**이야기** ✅ (015 실제 도입부)
```
월요일 아침.
책상에 파일 30개.
게임_최종.godot
게임_최종_진짜.godot
게임_최종_진짜_마지막.godot
어떤 게 되는 파일인지 모르겠다.
3일치 작업이 어딘가에 있는데 찾을 수가 없다.
```

**설명** ❌
```
Git은 분산 버전 관리 시스템으로,
소스 코드의 변경 이력을 추적하고 관리합니다.
commit을 통해 스냅샷을 저장하고 branch로 병렬 개발이 가능합니다.
```

### 구분 체크리스트

| 질문 | 이야기 ✅ | 설명 ❌ |
|------|---------|--------|
| 첫 문장에 사람이 있나? | "월요일 아침 에이전트가 죽었다" | "AI 에이전트란..." |
| 감정이 있나? | 빡침, 당황, 궁금 | 중립적 서술 |
| 시도→실패가 있나? | "해봤다. 안 됐다." | "방법은 다음과 같다" |
| 해결 안 되면 그냥 끝나나? | "아직 모르겠다" | "결론: 효과적이다" |
| 비유가 일상에서 나오나? | "엄마 옷장" | "TF-IDF 알고리즘" |
| 독자가 "나도 저래" 하나? | "ㅋㅋ 나도" | "아 그렇구나" |
